# Native coding implementation decisions

Status: proposed implementation contract, 6 October 2026. This planning request does not start product implementation. The lead freezes these decisions when execution is authorized, records any justified revision, and includes the current text in every implementation packet.

## Scope and authority

1. Extend the existing seven-crate workspace. No new framework, crate, provider SDK, scheduler, or dependency is planned. Keep SQL safety in saya-connectors, turn policy in saya-agent, capability mechanics in saya-harness, persistence in saya-store, configuration in saya-config, shared pure records in saya-types, and presentation/composition in saya-cli.
2. Reuse release/v0.4.2 at faa0a8c875ad2640eb5c2cdd5fee0c0f9161f65f as the planning baseline. Implementation starts from the then-current reviewed integration HEAD, never main's dirty checkout. Refresh stale packets after any upstream change. All work stays local; no push, PR, tag, release, deployment, or cloud CI publication.
3. Database operations remain bounded and read-only through existing connectors. New instructions, notes, preferences, checkpoints, and resumed records never grant capabilities. Preserve existing consent modes and host/sandbox distinctions; no default permission expansion is part of this plan.
4. Existing finite answering budgets, SQL cancellation, concurrency metadata, recovery and artifact gates are retained. Auxiliary work needs its own bounds; new notes must not inherit the database extractor's intentionally unbounded total wall-clock behavior.

## Cancellation

5. Extend existing ToolExecutionContext into fetch and scratch operations; do not add a second cancellation token system. A caller retains operation ownership until effects have settled. Blocking DuckDB queries must be interrupted through the existing handle and then joined. CSV import already uses a transaction and per-row deadline checks: add cooperative token checks around parsing, insertion and before commit; do not assert that all parsing is instantaneously interruptible. Wait for rollback/commit settlement and release the connection before continuing. No false success, detached write, or later tool effect after cancellation wins.
6. Download cancellation never publishes an incomplete destination. Preserve the existing bounded, digest-verified partial-download/resume contract; report retained partial state for an explicit retry, and clean only unowned/incomplete temporary state according to that contract. Do not delete a previously valid partial implicitly. Publication is a deliberate commit boundary: cancellation observed before it refuses publication; cancellation after completed publication reports the actual committed outcome. Record consumed bytes exactly once and never refund already consumed external work as if it did not happen.

## File edits and recovery

7. Require an observed digest for replacing existing files through agent edit/write tools; create is explicitly create-if-absent. Append guards include expected content digest and offset. Keep one per-path admission/commit policy reused by all write-shaped agent adapters, including writes that could otherwise bypass guarded edits. Internal artifact writers retain their own typed contracts; do not blindly change every write API.
8. These are optimistic stale-version guards, not a portable atomic filesystem compare-and-swap. Serialize Saya writers, compare the anchored target identity/content immediately before publication, and refuse detected changes. Do not promise protection from every non-cooperating external writer racing the final check. Document this limit and preserve recoverable originals. If the requested guarantee is stronger, schedule a separate isolation design before advertising it.
9. Checkpoints cover direct file-tool edits only. They never claim to undo subprocess, network, scratch, or production database effects. Restore is conditional on the current digest matching the recorded post-edit version, and never resets an entire Git checkout. Existing human changes are part of the baseline, not discarded.
10. Before-images are opt-in private source-file recovery data outside the project, separate from session narrative and database evidence. They preserve exact bytes; redacted bytes cannot be advertised as a faithful restore. Reject known credential paths, known-secret content and database-export artifacts from snapshot admission; surface recovery-unavailable without silently saving raw prohibited data. This screening is not a proof that arbitrary source contains no sensitive information. Explain retention when enabling recovery, do not enable it silently, and scan release artifacts so recovery data is never packaged.
11. Initial proposed recovery caps: 8 MiB per file (matching the existing workspace IO ceiling), 64 MiB per session and 128 edits per session. At quota, refuse a recovery-required edit before mutation; the user can explicitly delete checkpoints or disable recovery for later edits. No automatic history eviction. Checkpoint prepare/commit states distinguish pending, committed and uncertain effects after a crash. A snapshot failure never masquerades as a successful checkpoint.

## Context and memory

12. First instruction loader reads only workspace-root AGENTS.md and an optional personal instructions.md under the resolved user configuration directory. No recursive walk, implicit imports, ancestor escape, hooks, command execution, or CLAUDE.md compatibility layer initially. Use existing anchored reads for the project; personal files use an explicit configured root and bounded file IO. Treat both as context, never authority.
13. Initial instruction caps: project 32 KiB, personal 16 KiB, aggregate 48 KiB, maximum two files. Preserve UTF-8 boundaries and mark truncation. Fixed source order personal then project; current user intent and enforced policy prevail. Record source identity/hash and truncation in the context view. Context admission may trim these further; these caps are resource limits, not promises to include everything in a small model window.
14. Existing ContextBlock and request preflight remain the integration path. One CLI-owned projection assembles project instructions, permitted preferences, session continuation and observations; no second system prompt or parallel context scheduler. Cache keys include source digest, workspace, profile and relevant privacy classification. Reuse unchanged sources and bound every re-read; visibility changes invalidate before the next request.
15. Continuation is an additive, explicitly versioned optional session extension, with a validated source-turn boundary/hash over redacted persisted data. Keep stable source identity across filtering; never interpret compacted-turn count as an index after privacy filtering. Unknown extension versions cannot be silently overwritten by a reader that does not understand them.
16. Initial continuation cap 32 KiB serialized; narrative cap 8 KiB; at most 64 file references and 32 recorded checks. Reuse the existing task-list bounds. Preserve user-authored notes separately from generated narrative. Deterministic file/check facts come from actual operations, with source revision/time and provenance; model prose cannot certify a test or query. A digest detects source drift, not authenticity; persisted historical checks remain historical data, never fresh evidence or authority.
17. Redact continuation before disk, classify source sensitivity conservatively, and revalidate scope/privacy before model inclusion. No raw query cells, complete arbitrary tool outputs, credential values, or model reasoning. Reject or omit unsafe narrative with a visible reason. After resume, stale file checks are historical until revalidated; permissions are freshly resolved under existing rules.
18. No automatic permanent memory. Explicit project preference add/list/edit/forget first, stored separately from typed database knowledge in the existing SQLite store. Existing PreferenceValue intentionally excludes free prose and the existing table holds one value per kind: preserve that contract; use a separate project-guidance record/table while reusing store infrastructure. Default scope is canonical worktree identity; cross-worktree sharing is later opt-in, not an inferred repository-wide default. Initial caps: 64 preferences per worktree, 1 KiB text per preference, 16 KiB aggregate recall. Explicit user confirmation is the authority for a preference; it still grants no execution permissions.
19. Session notes/continuation remain in the session record, not a new independent database or free-form memory directory. Optional model summaries reuse the existing bounded summarizer. Never introduce a model call merely to record a deterministic event, and never make notes extraction an unbounded post-answer wait.

## Session lifecycle and compatibility

20. Keep the current 4 MiB session-record cap. Warn at 3 MiB using the same serialization accounting as the store. Offer explicit rotation into a successor session with bounded validated continuation and parent linkage; preserve the old transcript. No silent pruning. Refuse an individual oversize turn before losing the last good session, with a visible path to rotate/export.
21. Rotation is publish-successor then update selection, recoverable across crashes and retries. Never silently move active work or grants. Deletion is coordinated by saya-harness using its existing RunLock, not by introducing an upward dependency from saya-store. Store methods own tombstone/cleanup mechanics; a stable tombstone outside the removable tree is checked before and after session lock acquisition. Deletion requires the session's exclusive ownership lock, refuses an active session, uses validated identifiers and no-follow containment, and cleans session JSON, associated state and checkpoints together. Separate independent project preferences/database facts remain and must be named in the result. Tombstone/cleanup-pending state makes partial filesystem cleanup observable and retryable. Do not remove the lock inode while relying on it for exclusivity. Older binaries that ignore the tombstone must not operate concurrently on lifecycle-managed state.
22. Old sessions with no extension must retain current behavior. New readers validate the extension before use; unsupported/corrupt optional content cannot grant authority or destroy the old record. Before writing extended sessions, document that old binaries can discard unknown fields: downgrade is unsupported for writes without restoring a pre-upgrade backup. Do not silently bump SESSION_VERSION and assume every older reader rejects it.

## UX and scripted execution

23. Doctor exposes independent database/AI/workspace readiness. Preserve existing doctor exit semantics when no task is specified; add explicit --task query|ai|coding, with a truthful config-readiness exit. Do not equate configuration readiness with successful network authentication. Existing output fields are retained; additions are additive.
24. First run offers work on this project, connect a database, open a data file, or demo. Use the existing setup planner/writer and existing demo/open operations. Database setup remains optional for coding; AI setup remains optional for raw SQL/demo. Setup commits only after its existing review/confirmation and returns safely to the session without nested runtime or terminal ownership conflicts.
25. Provider setup may offer an already-present standard environment variable by NAME, bound to the selected provider/endpoint. Never enumerate or print secret values, auto-send a provider credential to a custom compatible endpoint, or add implicit .env loading. Keychain/OAuth are explicitly deferred, not silently implemented by the plan.
26. Prefer a narrow headless session entry using the existing --turn-file pipeline for scripted coding; preserve ask's current contract. Establish missing behavior through a capability matrix before adding syntax. No prompt on noninteractive runs; absent permission yields a typed refusal. Do not advertise full coding parity until the actual edit/test workflow works with explicit existing scope controls.
27. Config source explanation and reload are follow-on slices. Reload constructs a validated candidate runtime and applies it atomically between turns. Failed reload preserves the old configuration. Host/deny/approval changes require existing session-recomposition semantics, not a mid-turn authority change. If this cannot be achieved narrowly, ship explanation first and retain documented restart behavior.

## Operational bounds

28. Three GLM implementation/research worker slots plus the lead. One writer per worktree and per owned file. Worktrees do not remove shared-file semantic conflicts. At most two concurrent Cargo jobs initially; reduce based on observed memory/disk pressure. Keep at least 40 GiB free before fresh parallel builds; preserve user targets, active targets and DuckDB/compiler caches.
29. Target one observable outcome per packet and 20–45 minutes of active implementation, excluding build queues. Split after a failed handoff or when a packet requires multiple independent behaviors. These are sizing heuristics, not timing guarantees. Every new or changed test passes the four-question test-audit authoring gate; no campaign pruning is authorized.
30. Shared parser/dispatch, runtime/context composition, public exports, session wire formats, migrations, tool registry and root manifests receive exclusive leases. Backend packets integrate before adapters. The lead reviews each report/diff, independently validates immutable source, merges locally, checks all targets after every merge, and records exact commit/evidence before releasing dependents.
